## Part 2: 🕵️ Tester — เปลี่ยนวิธีคิด
*เปลี่ยนจาก “โปรแกรมทำงานอย่างไร?” เป็น “เราจะพิสูจน์ได้อย่างไรว่าระบบทำงานถูกต้อง?”*

### 2.1 คุณจะทดสอบส่วนนี้อย่างไร?
> ใช้เทคนิค **Black-box Testing** โดยแบ่งข้อมูลออกเป็นกลุ่มสมมูล **Equivalence Partitioning (EP)** ทั้งกลุ่มข้อมูลที่ถูกต้อง (Valid) และไม่ถูกต้อง (Invalid) ร่วมกับการวิเคราะห์ค่าขอบเขต **Boundary Value Analysis (BVA)** เพื่อทดสอบที่จุดรอยต่อของเงื่อนไข (เช่น ความยาวชื่อ 3 และ 4 ตัวอักษร, อายุ 14 ปีเศษ กับ 15 ปีบริบูรณ์, เบอร์โทร 8, 9, 10, 11 หลัก) และตรวจดูพฤติกรรมของ UI ทั้งตอนเลื่อนออกจากช่อง (Blur) และตอนกด Submit

### 2.2 คุณจะใช้ Test Data อะไร?
> ออกแบบชุดข้อมูลทดสอบครอบคลุม 4 มิติ:
> 1. ข้อมูลปกติ (Valid Normal Data): เช่น ชื่อ `"Kitsakon Sarakhan"`, เบอร์ `"0812345678"`
> 2. ข้อมูลค่าขอบเขต (Boundary Data): เช่น วันเกิดที่อายุครบ 15 ปีพอดี และขาดอีก 1 วัน
> 3. ข้อมูลผิดเงื่อนไข (Invalid Data): เช่น อีเมลไม่มี `@`, เบอร์โทรขึ้นต้นด้วย `1`, ใส่วันที่ในอนาคต
> 4. ข้อมูลว่าง (Empty Data): เว้นว่างช่องที่จำเป็นทุกช่องแล้วกด Submit

### 2.3 ผลลัพธ์ที่คาดหวังคืออะไร? (Expected Result)
> * **กรณีข้อมูลถูกต้อง:** ช่องกรอกต้องไม่มีกรอบสีแดง ไม่แสดงข้อความ Error และเมื่อกรอกครบทุกช่องสามารถ Submit สำเร็จได้ Toast แจ้งเตือน
> * **กรณีข้อมูลไม่ถูกต้อง/ผิดเงื่อนไข:** ระบบต้องดักจับได้ทันที แสดงกรอบสีแดงพร้อมข้อความแจ้งเตือนที่ตรงกับจุดผิด และไม่อนุญาตให้ส่งฟอร์ม

### 2.4 ผลลัพธ์ที่เกิดขึ้นจริงคืออะไร? (Actual Result)
> ระบบส่วนใหญ่สามารถตรวจสอบและขึ้นข้อความแจ้งเตือนได้ถูกต้อง แต่พบว่าในบางช่อง เช่น วันเกิด มีการคำนวณอายุเฉพาะปี ค.ศ. ทำให้ผู้ที่อายุยังไม่ครบ 15 ปีบริบูรณ์ผ่านการคัดกรองได้ และช่อง Full name สามารถกรอกชื่อเพียงคำเดียวโดยไม่มีนามสกุลก็ผ่านได้

### 2.5 คุณจะตัดสิน PASS หรือ FAIL จากอะไร?
> ตัดสินโดยนำ **ผลลัพธ์ที่เกิดขึ้นจริง (Actual Result)** ไปเปรียบเทียบกับ **ผลลัพธ์ที่คาดหวังตามข้อกำหนด (Expected Result)**:
> * หากผลจริงตรงกับผลที่คาดหวัง $\rightarrow$ ตัดสินเป็น **PASS**
> * หากผลจริงขัดแย้งกับผลที่คาดหวัง หรือระบบทำงานไม่ตรงตามสเปก $\rightarrow$ ตัดสินเป็น **FAIL** (และบันทึกข้อผิดพลาดเพื่อทำ Bug Report)

### วิเคราะห์ปัญหาที่พบ (เลือกกรณีที่ 5: ช่องวันเกิด `birthDate`):

### 3.1 พบปัญหาอะไร?
> ฟังก์ชันตรวจสอบวันเกิด (`birthDate`) คำนวณอายุโดยการนำปี ค.ศ. ปัจจุบัน ลบด้วยปี ค.ศ. เกิดโดยตรง ($2026 - 2011 = 15$) ส่งผลให้ผู้สมัครที่เกิดปลายปี 2011 ซึ่งมีอายุจริงเพียง 14 ปี 8 เดือน (ยังไม่ครบ 15 ปีบริบูรณ์) สามารถผ่านเกณฑ์การสมัครได้

### 3.2 คุณทำอย่างไรจึงพบปัญหานี้?
> ใช้เทคนิค Boundary Value Analysis (BVA) โดยทดสอบป้อนวันเกิดของปีที่จะครบ 15 ปี แต่เลือกวันที่ปลายปี (เดือนธันวาคม) เพื่อทดสอบว่าระบบมีการนำเดือนและวันเกิดจริงมาหักลบด้วยหรือไม่

### 3.3 Expected Result ของกรณีนี้คืออะไร?
> ระบบต้องไม่อนุญาตให้ผ่าน โดยแสดงกรอบสีแดงที่ช่อง Date of birth และขึ้นข้อความแจ้งเตือน *"Applicants must be at least 15 years old."*

### 3.4 Actual Result ที่เกิดขึ้นจริงคืออะไร?
> ช่อง Date of birth แสดงสถานะปกติ ไม่ขึ้นข้อความเตือน และยอมให้กดส่งใบสมัครผ่านได้สำเร็จ

### 3.5 มีหลักฐานอะไร เช่น Screenshot / ข้อมูลที่ใช้ทดสอบ?
> ภาพหน้าจอขณะเลือกวันที่ `31/12/2011` แล้วกดส่งฟอร์มสำเร็จ (Toast แจ้งเตือนแสดงขึ้นมา) และ Source Code ในไฟล์ `outputs/script.js` บรรทัดที่ 15 ที่ระบุสูตร:

### 5.3 เพราะเหตุใดจึงสรุปผลเช่นนั้น?
> เพราะหลังจาก Developer แก้ไขโค้ดให้มีการคำนวณเปรียบเทียบเดือนและวันเกิดจริง (`const m = now.getMonth() - d.getMonth(); if (m < 0 || (m === 0 && now.getDate() < d.getDate())) age--;`) เมื่อทดสอบกรอกวันที่ `31/12/2011` ระบบสามารถคำนวณอายุได้ 14 ปี และแสดงกรอบสีแดงพร้อมข้อความเตือน *"Applicants must be at least 15 years old."* ตรงตามข้อกำหนดทุกประการ

## Part 6: 💡 Reflection — จาก Developer สู่ Tester

### 6.1 วันนี้คุณเรียนรู้อะไรเกี่ยวกับ Software Testing?
> ได้เรียนรู้ว่าการทดสอบซอฟต์แวร์เป็นกระบวนการที่มีแบบแผนและหลักการทางวิศวกรรม ไม่ใช่การสุ่มกดเล่นตามความรู้สึก เริ่มตั้งแต่การทำความเข้าใจความต้องการของระบบ (Requirement), การสวมบทบาทเป็นผู้ใช้เพื่อออกแบบ Test Data ด้วยเทคนิค EP และ BVA, การสังเกตและบันทึกผลตามหลักฐานจริง ไปจนถึงการสื่อสารข้อผิดพลาดผ่าน Bug Report ที่มีมาตรฐาน

### 6.2 Developer กับ Tester ต้องคิดต่างกันอย่างไร?
> * **Developer (ผู้สร้าง):** คิดในมุม **"ทำอย่างไรให้ระบบทำงานได้" (Constructive / How to make it work)** มักโฟกัสที่เส้นทางปกติที่ผู้ใช้กรอกข้อมูลถูกต้อง (Happy Path)
> * **Tester (ผู้พิสูจน์):** คิดในมุม **"ทำอย่างไรจึงจะพิสูจน์ได้ว่าระบบทำงานถูกต้องในทุกสภาวะ" (Destructive & Investigative / How to break it)** มุ่งค้นหาจุดบกพร่อง ค่าขอบเขต และเคสผิดปกติที่ผู้พัฒนาอาจมองข้าม

### 6.3 ทำไม Tester ต้องคิดถึงกรณีที่ผู้ใช้กรอกข้อมูลผิด?
> เพราะในการใช้งานจริง ผู้ใช้มีความหลากหลาย อาจพิมพ์ข้อมูลผิด พิมพ์ไม่ครบ ไม่เข้าใจรูปแบบ หรือแม้กระทั่งพยายามส่งข้อมูลไม่พึงประสงค์เข้ามา หากระบบไม่เตรียมพร้อมรับมือข้อมูลที่ผิดพลาด ระบบอาจทำงานล้มเหลว (Crash), ฐานข้อมูลเสียหาย หรือเกิดช่องโหว่ด้านความปลอดภัย

### 6.4 สิ่งที่ยากที่สุดในการหา Bug วันนี้คืออะไร?
> สิ่งที่ยากที่สุดคือการค้นหาข้อผิดพลาดเชิงตรรกะธุรกิจ (**Business Logic Defect**) หรือบั๊กที่ค่าขอบเขต (Boundary Value) ซึ่งเป็นบั๊กที่ไม่ทำให้โปรแกรมหยุดทำงาน (Crash) และไม่มีข้อความแจ้งเตือนสีแดงใน Console ซึ่งหากไม่สังเกตและไม่ออกแบบข้อมูลทดสอบที่ค่าขอบเขตอย่างตั้งใจ ก็จะไม่สามารถค้นพบบั๊กเหล่านี้ได้เลย
