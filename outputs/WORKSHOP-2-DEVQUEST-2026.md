## หน้า 3: MISSION 1 — FIND THE DATA

### STEP 1: เลือกตัวแปรจริง
* **ชื่อตัวแปร:** `valid` (ในฟังก์ชัน `validateField`)
* **ชนิดข้อมูล:** `boolean` (`true` / `false`)
* **เหตุผลที่เลือกตัวแปรนี้:**
  > ตัวแปร `valid` ในฟังก์ชัน `validateField` (บรรทัดที่ 28–34 ใน `script.js`) เป็นตัวแปรหัวใจหลักของการตรวจสอบความถูกต้องของข้อมูลทุกช่องในฟอร์ม DevQuest 2026 (`fullName`, `email`, `phone`, `birthDate`, `experience`, `contactMethod`, `portfolio`) โดยมีการนิยามค่า (Def) จากการประเมินกฎ Validation, นำไปใช้เป็นเงื่อนไขในการตัดสินใจ (P-use) เพื่อเลือกว่าจะแสดงหรือเคลียร์ข้อความเตือน และส่งค่าคืนกลับไป (C-use) ให้กับการประมวลผลการส่งฟอร์ม (Form Submission) ทำให้เห็นพฤติกรรมการไหลของข้อมูล (Data Flow) ได้อย่างชัดเจนมากที่สุด

### STEP 2: หา Def และ Use

**Source Code ที่พิจารณา (`outputs/script.js` บรรทัดที่ 28–34):**
```javascript
28: function validateField(id) {
29:   const element = document.querySelector(`#${id}`);
30:   const rule = requiredFields[id];
31:   const valid = rule.validate(element.value);
32:   setError(element, valid ? '' : rule.message);
33:   return valid;
34: }
```
*(และฟังก์ชัน `setError` บรรทัดที่ 21–26):*
```javascript
21: function setError(element, message = '') {
22:   const field = element.closest('.field');
23:   if (!field) return;
24:   field.classList.toggle('invalid', Boolean(message));
25:   field.querySelector('.error').textContent = message;
26: }
```

**ตารางแจกแจง Def และ Use:**

| ลำดับ/บรรทัด | เกิดอะไรขึ้นกับตัวแปร? | ฉันจัดเป็น | หลักฐาน/เหตุผล |
| :---: | :--- | :---: | :--- |
| **บรรทัด 31** | `const valid = rule.validate(element.value);` | **[x] Def**<br>[ ] Use | มีการกำหนดค่าเริ่มต้นให้กับตัวแปร `valid` ด้วยเครื่องหมาย `=` จากผลลัพธ์ของฟังก์ชัน validate |
| **บรรทัด 32 (ก)** | `valid ? '' : rule.message` (ส่วนประเมินเงื่อนไข Ternary Operator) | [ ] Def<br>**[x] Use** | มีการดึงค่าของ `valid` มาตรวจสอบในเชิงตรรกะว่าจริงหรือเท็จ เพื่อเลือกข้อความที่จะส่งให้ `setError` (**P-use**) |
| **บรรทัด 32 (ข)** | ส่งค่าผลลัพธ์ `''` ไปยัง `setError` เมื่อ `valid === true` | [ ] Def<br>**[x] Use** | ผลจากการตัดสินใจของ `valid` ทำให้เกิดการเรียกใช้คำสั่งเคลียร์สถานะ invalid ออกจาก UI |
| **บรรทัด 32 (ค)** | ส่งค่าผลลัพธ์ `rule.message` ไปยัง `setError` เมื่อ `valid === false` | [ ] Def<br>**[x] Use** | ผลจากการตัดสินใจของ `valid` ทำให้เกิดการเรียกใช้คำสั่งเพิ่มคลาส invalid และแสดงข้อความ error สีแดง |
| **บรรทัด 33** | `return valid;` | [ ] Def<br>**[x] Use** | นำค่าของตัวแปร `valid` ส่งออกไป (Return) เพื่อให้ฟังก์ชัน `form.submit` นำไปรวบรวมสถานะ (**C-use**) |

## หน้า 4: STEP 3 แยก P-use / C-use

| ตำแหน่ง (บรรทัด) | ตัวแปร | P-use หรือ C-use? | เหตุผลสั้น ๆ |
| :---: | :---: | :---: | :--- |
| **บรรทัด 32** | `valid` | **P-use** | ถูกใช้เป็นเงื่อนไขตัดสินใจ (Predicate) ใน Ternary Operator (`valid ? '' : rule.message`) |
| **บรรทัด 33** | `valid` | **C-use** | ถูกส่งคืนค่ากลับ (Return computation value) ไปให้ฟังก์ชันผู้เรียกใช้งานนำไปประมวลผลต่อ |
| **บรรทัด 63** | `fieldsValid` | **P-use** | ถูกนำไปใช้ร่วมกับ `roleValid`, `topicValid`, `termsValid` ในเงื่อนไข `if (!isFormValid)` |

### หยุดคิดก่อนเรียนคำศัพท์ต่อ
* **คำถาม:** ถ้าไม่มีคำว่า Def / Use / P-use / C-use เราจะอธิบายการเดินทางของค่าตัวแปรนี้ด้วยภาษาของเราเองว่าอย่างไร?
* **คำตอบ:**
  > "ตัวแปร `valid` เกิดขึ้นมาจากการ **'ตัดสินผลตรวจ'** ว่าข้อมูลที่ผู้ใช้พิมพ์เข้ามาในช่องนั้นถูกต้องตามกฎหรือไม่ (ได้ผลเป็น จริง หรือ เท็จ) จากนั้นเดินทางไป **'เป็นตัวแยกทางทำงาน'** ถ้าผ่าน (จริง) ก็จะสั่งล้างสีแดงเตือนบนหน้าจอ แต่ถ้าไม่ผ่าน (เท็จ) ก็จะสั่งให้หน้าจอโชว์กรอบแดงพร้อมข้อความแจ้งเตือน แล้วสุดท้ายส่ง **'ใบรายงานผล'** นี้กลับไปให้ระบบใหญ่ เพื่อนำไปรวมกับช่องอื่น ๆ ว่าอนุญาตให้กดส่งใบสมัครได้หรือยัง"

## หน้า 5: MISSION 2 — TRACE THE DATA

### STEP 1: วาด Data Map อย่างง่าย
```text
[Def] คำนวณผลตรวจ valid = rule.validate(value) (บรรทัด 31)
       │
       ▼
[P-use] ตรวจสอบค่าตัวแปร valid (บรรทัด 32)
   ├── (กรณี valid == true) ──► ส่งค่า '' เข้า setError -> ปลดคลาส invalid / ล้างข้อความ error
   └── (กรณี valid == false) ─► ส่งค่า rule.message เข้า setError -> ใส่คลาส invalid / แสดงข้อความ error
       │
       ▼
[C-use] return valid ส่งค่ากลับไปให้ Array .every(Boolean) ที่รอรับใน form.submit (บรรทัด 33)
       │
       ▼
[P-use] นำ fieldsValid ไปเช็กเงื่อนไข if (!...) เพื่ออนุญาตให้แสดง Toast สำเร็จ หรือ สกอร์ลไปหาจุดผิด (บรรทัด 67)
```
*(เขียนสรุปย่อตามแนวคิดใบงาน:)*  
`Def (ตรวจค่า input) -> P-use (แยกเงื่อนไข true/false) -> C-use (อัปเดต UI หน้าเว็บ) -> C-use (return ค่าสถานะ) -> P-use (ตัดสินใจ submit ฟอร์ม)`

### STEP 2: เรียนรู้ Data Flow Testing

| คำถาม | คำตอบของฉัน |
| :--- | :--- |
| **Data Flow Testing มองอะไรในโปรแกรม?** | DFT มอง **"พฤติกรรมและการเดินทางของตัวแปร (Data Flow)"** ภายในโปรแกรม โดยจับตาดูว่าตัวแปรถูกสร้าง/กำหนดค่าที่ไหน (Def) ถูกนำไปใช้คำนวณที่ไหน (C-use) และถูกนำไปใช้เป็นเงื่อนไขตัดสินใจที่ไหน (P-use) เพื่อตรวจจับความผิดปกติของข้อมูล แทนที่จะมองเพียงลำดับคำสั่งทีละบรรทัด |
| **ทำไมการติดตามตัวแปรจึงช่วยในการทดสอบ?** | เพราะความผิดพลาดในซอฟต์แวร์ส่วนใหญ่เกิดจากข้อมูลผิดสถานะ (เช่น ตัวแปรไม่มีค่าแต่ถูกนำไปใช้, ค่าที่ได้ไม่ตรงตามขอบเขต, หรือค่าถูกเขียนทับ) การติดตามตัวแปรช่วยให้เราเจาะจงสร้าง Test Case ที่ทดสอบเฉพาะเส้นทางของข้อมูลที่สำคัญได้โดยตรง ช่วยประหยัดเวลาและครอบคลุมจุดวิกฤตได้ดีกว่าการสุ่มทดสอบเส้นทางใน Control Flow |

## หน้า 6: STEP 3 เรียนรู้ Def-Use Pair และ Def-Clear Path

กำหนดหมายเลขโหนดของฟังก์ชัน `validateField`:
* **โหนด 1 (บรรทัด 29–30):** ดึง `element` และดึง `rule`
* **โหนด 2 (บรรทัด 31):** `Def(valid)` จาก `rule.validate(element.value)`
* **โหนด 3 (บรรทัด 32):** `P-use(valid)` ในเงื่อนไข Ternary (`valid ? ... : ...`)
* **โหนด 4 (บรรทัด 32 กิ่งจริง):** `setError(element, '')` (เคลียร์ error)
* **โหนด 5 (บรรทัด 32 กิ่งเท็จ):** `setError(element, rule.message)` (แสดง error)
* **โหนด 6 (บรรทัด 33):** `C-use(valid)` ในคำสั่ง `return valid`

**ตารางจับคู่ Def-Use:**

| Def จุดที่ | Use จุดที่ | เป็น Def-Use Pair หรือไม่? | เหตุผล |
| :---: | :---: | :---: | :--- |
| **โหนด 2 (บรรทัด 31)** | **โหนด 3 (บรรทัด 32)** | **[x] ใช่** [ ] ไม่ใช่ | ค่า `valid` ที่ถูกนิยามที่โหนด 2 เดินทางตรงมาถูกตรวจสอบเงื่อนไขที่โหนด 3 ทันทีโดยไม่มีการกำหนดค่าใหม่คั่นกลาง (Def-clear path) |
| **โหนด 2 (บรรทัด 31)** | **โหนด 6 (บรรทัด 33)** *(ผ่านโหนด 4)* | **[x] ใช่** [ ] ไม่ใช่ | ในเส้นทาง `2 -> 3 -> 4 -> 6` ค่า `valid` ถูกส่งกลับ (return) โดยไม่มีคำสั่งแก้ไขค่า `valid` ในโหนด 4 เลย |
| **โหนด 2 (บรรทัด 31)** | **โหนด 6 (บรรทัด 33)** *(ผ่านโหนด 5)* | **[x] ใช่** [ ] ไม่ใช่ | ในเส้นทาง `2 -> 3 -> 5 -> 6` ค่า `valid` ถูกส่งกลับ (return) โดยไม่มีคำสั่งแก้ไขค่า `valid` ในโหนด 5 เช่นกัน |
| **โหนด 1 (บรรทัด 29)** | **โหนด 6 (บรรทัด 33)** | [ ] ใช่ **[x] ไม่ใช่** | โหนด 1 เป็นการนิยามตัวแปร `element` ไม่ใช่ `valid` จึงไม่สามารถจับคู่เป็น Def-Use Pair ของตัวแปร `valid` ได้ |

## หน้า 7: MISSION 2 — TRACE THE DATA (ต่อ)

### STEP 4: ค้นหา “3 ขั้นตอน” ของ Data Flow Testing

| ขั้นตอน | สิ่งที่ฉันเข้าใจ |
| :---: | :--- |
| **1** | **การสร้างกราฟกระแสข้อมูล (Data Flow Graph: DFG):** แปลงโค้ดฟังก์ชันให้อยู่ในรูปของโหนดและเส้นเชื่อมตามลำดับการทำงาน พร้อมเขียนกำกับว่าแต่ละโหนดเกิด `Def`, `C-use`, หรือ `P-use` สำหรับตัวแปรใด |
| **2** | **การสร้างเส้นทางทดสอบ (Def-Use Paths):** วิเคราะห์หาเส้นทางที่เชื่อมโยงระหว่างจุดกำหนดค่า (Def) ไปยังจุดเรียกใช้ค่า (Use) โดยเป็นเส้นทางที่ไม่มีการเขียนทับค่า (Def-Clear Path) |
| **3** | **การสร้างกรณีทดสอบ (Test Cases):** ออกแบบข้อมูลนำเข้า (Input Data) ที่เจาะจงให้โปรแกรมวิ่งผ่านแต่ละ Path ที่เลือกไว้ พร้อมทั้งคำนวณและระบุผลลัพธ์ที่คาดหวัง (Expected Result) |

### STEP 5: สร้าง Mini Data Flow Graph (DFG)
```text
              [ โหนด 1: ดึง element & rule ]
                            │
                            ▼
              [ โหนด 2: Def(valid) ]  (บรรทัด 31)
                            │
                            ▼
              [ โหนด 3: P-use(valid) ] (บรรทัด 32)
                       /         \
                 (จริง: true)   (เท็จ: false)
                     /             \
                    ▼               ▼
          [ โหนด 4: เคลียร์ error ]  [ โหนด 5: แสดง error ]
                    \               /
                     \             /
                      ▼           ▼
              [ โหนด 6: C-use(valid) -> return ] (บรรทัด 33)
```

### STEP 6: สร้าง Def-Use Paths (หน้า 7–8)
*(ทดสอบร่วมกับกฎของฟิลด์ `birthDate` และ `fullName` เพื่อให้เห็นชุดข้อมูลที่ชัดเจน)*

| Path | เส้นทางที่ฉันพบ | Def -> Use ที่เกี่ยวข้อง |
| :---: | :--- | :--- |
| **Path-1** | `1 -> 2 -> 3 -> 4 -> 6` | `Def(โหนด 2) -> P-use(โหนด 3) -> C-use(โหนด 6)` (กรณีข้อมูลถูกต้อง `valid === true` $\rightarrow$ เคลียร์ error แล้ว return true) |
| **Path-2** | `1 -> 2 -> 3 -> 5 -> 6` | `Def(โหนด 2) -> P-use(โหนด 3) -> C-use(โหนด 6)` (กรณีข้อมูลผิดพลาด `valid === false` $\rightarrow$ แสดงข้อความ error แล้ว return false) |
| **Path-3** | `Path-1 -> Submit Pass` | `C-use(โหนด 6) -> fieldsValid (True) -> P-use (Line 67)` (ทุกช่องผ่านฟอร์มส่งสำเร็จ แสดง Toast) |
| **Path-4** | `Path-2 -> Submit Fail` | `C-use(โหนด 6) -> fieldsValid (False) -> P-use (Line 67)` (มีช่องไม่ผ่าน บล็อกการส่งและเลื่อนจอไปหาจุดผิด) |

## หน้า 15: REFLECTION — ฉันเข้าใจ Data Flow Testing แล้วหรือยัง?

**1. ก่อนทำกิจกรรมนี้ ฉันคิดว่า Test Case เกิดขึ้นจากอะไร?**
> *"ก่อนทำกิจกรรมนี้ ฉันคิดว่า Test Case เกิดจากการสุ่มใส่ข้อมูลตามใจชอบ หรือดูแค่หน้าตา UI ว่ามีช่องอะไรให้พิมพ์บ้าง แล้วลองพิมพ์มั่ว ๆ ลงไปดูว่าจะพังหรือไม่ โดยไม่ได้คำนึงถึงว่าโค้ดหลังบ้านทำงานอย่างไร"*

**2. หลังทำกิจกรรมนี้ ฉันเห็นความสัมพันธ์ระหว่าง Source Code กับ Test Case อย่างไร?**
> *"หลังทำกิจกรรมนี้ ฉันเห็นอย่างชัดเจนว่า Source Code คือพิมพ์เขียวของ Test Case ทุกชุดข้อมูลนำเข้าถูกออกแบบขึ้นมาอย่างมีเป้าหมายเพื่อบังคับให้ตัวแปรใน Source Code เดินทางผ่านเส้นทาง Def-Use แต่ละเส้นที่กำหนดไว้ได้อย่างแม่นยำ"*

**3. Def และ Use ช่วยให้ฉันมองหาเส้นทางทดสอบได้อย่างไร?**
> *"ช่วยเป็นตัวกรองที่ยอดเยี่ยม ทำให้เราไม่ต้องเสียเวลาทดสอบทุกเส้นทางที่เป็นไปได้ของโปรแกรม แต่โฟกัสเฉพาะจุดที่ข้อมูลถือกำเนิดขึ้น (Def) และจุดที่ข้อมูลถูกดึงไปตัดสินใจหรือประมวลผล (Use) ทำให้ครอบคลุมจุดวิกฤตของระบบได้ครบถ้วนโดยใช้จำนวน Test Case น้อยที่สุด"*

**4. จุดไหนของกิจกรรมที่ฉันยังไม่เข้าใจ และต้องการให้อาจารย์อธิบายเพิ่ม?**
> *"อยากให้อาจารย์อธิบายเพิ่มเติมเกี่ยวกับการทำ Data Flow Testing กับฟังก์ชันที่ทำงานแบบ Asynchronous (เช่น Event Listener, Promise, หรือ Fetch API) ว่ามีหลักการลากเส้น DFG และระบุ Def-Clear Path อย่างไรเมื่อลำดับเวลาไม่แน่นอน"*

**5. ถ้าต้องกลับไปทดสอบเว็บไซต์ของตนเองอีกครั้ง ฉันจะปรับวิธีคิด/วิธีทดสอบอย่างไร?**
