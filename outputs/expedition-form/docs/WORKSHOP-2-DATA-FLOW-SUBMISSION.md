## หน้า 3: MISSION 1 — FIND THE DATA

### STEP 1: เลือกตัวแปรจริง
* **ชื่อตัวแปร:** `age`
* **ชนิดข้อมูล:** `number` (Integer)
* **เหตุผลที่เลือกตัวแปรนี้:**
  > ตัวแปร `age` มีวงจรชีวิตและการไหลของข้อมูล (Data Flow) ที่สมบูรณ์และชัดเจนมากที่สุดในระบบ โดยมีการนิยามค่าเริ่มต้นจากการคำนวณปี (Def), มีการนำค่าเดิมไปลบออกเพื่อปรับยอดตามเงื่อนไขเดือน/วันเกิด (C-use และ Re-def), และถูกนำไปใช้เป็นเงื่อนไขตัดสินใจทางตรรกะ (P-use) หลายจุดเพื่อตรวจสอบคุณสมบัติผู้สมัคร (ต้องอายุครบ 18 ปีบริบูรณ์ และไม่เกิน 80 ปี) ก่อนส่งผลลัพธ์ ทำให้เห็นพฤติกรรมของข้อมูลครบทุกรูปแบบตามทฤษฎี Data Flow Testing

### STEP 2: หา Def และ Use

**Source Code ที่พิจารณา (ฟังก์ชัน `dob` ใน `index.html` บรรทัดที่ 541–552):**
```javascript
541: dob: function(){
542:   var v = $("#dob").value;
543:   if(!v) return "กรุณาเลือกวันเกิด";
544:   var d = new Date(v), now = new Date();
545:   if(isNaN(d.getTime())) return "รูปแบบวันที่ไม่ถูกต้อง";
546:   if(d > now) return "วันเกิดต้องไม่เป็นวันในอนาคต";
547:   var age = now.getFullYear() - d.getFullYear();
548:   if(now.getMonth() < d.getMonth() || (now.getMonth() === d.getMonth() && now.getDate() < d.getDate())) age--;
549:   if(age < 18) return "ผู้สมัครต้องมีอายุครบ 18 ปีบริบูรณ์";
550:   if(age > 80) return "กรุณาตรวจสอบปีเกิดอีกครั้ง";
551:   return null;
552: }
```

**ตารางแจกแจง Def และ Use:**

| ลำดับ/บรรทัด | เกิดอะไรขึ้นกับตัวแปร? | ฉันจัดเป็น | หลักฐาน/เหตุผล |
| :---: | :--- | :---: | :--- |
| **บรรทัด 547** | `var age = now.getFullYear() - d.getFullYear();` คำนวณอายุตั้งต้นจากปี | **[x] Def**<br>[ ] Use | มีการประกาศตัวแปรและกำหนดค่าเริ่มต้นด้วยเครื่องหมาย `=` |
| **บรรทัด 548 (ก)** | `age--` (ส่วนดึงค่ามาลบ: `age - 1`) | [ ] Def<br>**[x] Use** | มีการเรียกอ่านค่าของ `age` ไปคำนวณคณิตศาสตร์ทางพีชคณิต (C-use) |
| **บรรทัด 548 (ข)** | `age--` (ส่วนบันทึกค่ากลับ: `age = ...`) | **[x] Def**<br>[ ] Use | มีการเขียนทับค่าใหม่ลงในตัวแปร `age` เดิม (Re-define) |
| **บรรทัด 549** | `if(age < 18)` ตรวจสอบเงื่อนไขอายุขั้นต่ำ | [ ] Def<br>**[x] Use** | นำค่า `age` ไปใช้ในนิพจน์เงื่อนไขการตัดสินใจของประโยค `if` (P-use) |
| **บรรทัด 550** | `if(age > 80)` ตรวจสอบเงื่อนไขอายุสูงสุด | [ ] Def<br>**[x] Use** | นำค่า `age` ไปใช้ในนิพจน์เงื่อนไขการตัดสินใจของประโยค `if` (P-use) |

## หน้า 4: STEP 3 แยก P-use / C-use

| ตำแหน่ง (บรรทัด) | ตัวแปร | P-use หรือ C-use? | เหตุผลสั้น ๆ |
| :---: | :---: | :---: | :--- |
| **บรรทัด 548** | `age` | **C-use** | ถูกนำไปใช้คำนวณทางคณิตศาสตร์ (ลดค่าลง 1 ในคำสั่งลดค่า `age--`) |
| **บรรทัด 549** | `age` | **P-use** | ถูกนำไปใช้ในนิพจน์เงื่อนไขตรรกะ (`age < 18`) เพื่อควบคุมทิศทางการคืนค่าแจ้งเตือน |
| **บรรทัด 550** | `age` | **P-use** | ถูกนำไปใช้ในนิพจน์เงื่อนไขตรรกะ (`age > 80`) เพื่อควบคุมทิศทางการคืนค่าแจ้งเตือน |

### หยุดคิดก่อนเรียนคำศัพท์ต่อ
* **คำถาม:** ถ้าไม่มีคำว่า Def / Use / P-use / C-use เราจะอธิบายการเดินทางของค่าตัวแปรนี้ด้วยภาษาของเราเองว่าอย่างไร?
* **คำตอบ:**
  > "ตัวแปร `age` เกิดขึ้นมาจากการ **'ตั้งต้นคำนวณ'** ด้วยการเอาปีปัจจุบันลบด้วยปีเกิด จากนั้นเดินทางต่อไปยังจุดตรวจว่าถึงวันเกิดปีนี้หรือยัง ถ้ายังไม่ถึงก็จะถูก **'ปรับลดลง 1 ปี'** แล้วค่าอายุที่ได้จะถูกส่งต่อไป **'ตรวจวัดเกณฑ์สองรอบ'** รอบแรกตรวจว่าเด็กไปไหม (< 18) รอบสองตรวจว่าแก่เกินไปไหม (> 80) หากผ่านทั้งสองด่าน ข้อมูลนี้ก็จะได้รับการยืนยันว่าถูกต้อง"

## หน้า 5: MISSION 2 — TRACE THE DATA

### STEP 1: วาด Data Map อย่างง่าย
```text
[Def] คำนวณอายุจากปี (บรรทัด 547)
       │
       ▼
   ตรวจเดือนและวันเกิด (บรรทัด 548)
   ├── (ยังไม่ถึงวันเกิดในปีนี้) ──► [C-use & Re-Def] ปรับลดค่า age-- (บรรทัด 548)
   │                                           │
   └── (ถึงวันเกิดแล้วในปีนี้) ───────────────────┘
       │
       ▼
[P-use] ตรวจสอบเงื่อนไข age < 18 (บรรทัด 549)
   ├── (จริง) ──► คืนค่าข้อความ: "ผู้สมัครต้องมีอายุครบ 18 ปีบริบูรณ์"
   └── (เท็จ)
       │
       ▼
[P-use] ตรวจสอบเงื่อนไข age > 80 (บรรทัด 550)
   ├── (จริง) ──► คืนค่าข้อความ: "กรุณาตรวจสอบปีเกิดอีกครั้ง"
   └── (เท็จ) ──► คืนค่า null (ผ่านการตรวจสอบ / ไม่พบข้อผิดพลาด)
```
*(เขียนสรุปย่อตามแนวคิดใบงาน:)*  
`Def (คำนวณปีเกิด) -> P-use (ตรวจวันเกิด) -> C-use & Def (ลดอายุ 1 ปี) -> P-use (เช็ก < 18) -> P-use (เช็ก > 80) -> คืนผลลัพธ์`

### STEP 2: เรียนรู้ Data Flow Testing

| คำถาม | คำตอบของฉัน |
| :--- | :--- |
| **Data Flow Testing มองอะไรในโปรแกรม?** | DFT มอง **"พฤติกรรมและวงจรชีวิตของตัวแปร (Data Lifecycle)"** ตลอดการประมวลผล ได้แก่ จุดที่ตัวแปรถูกสร้างหรือกำหนดค่า (Define), จุดที่ตัวแปรถูกนำไปคำนวณหรือแสดงผล (C-use), และจุดที่ตัวแปรถูกใช้เป็นเงื่อนไขตัดสินใจ (P-use) เพื่อดูว่าข้อมูลเดินทางอย่างถูกต้องหรือไม่ |
| **ทำไมการติดตามตัวแปรจึงช่วยในการทดสอบ?** | เพราะข้อบกพร่อง (Bugs) ในโปรแกรมมักเกิดจากสถานะของข้อมูลผิดพลาด (เช่น นำตัวแปรไปใช้ก่อนกำหนดค่า, คำนวณผิดแล้วส่งต่อ, หรือค่าถูกเขียนทับ) การติดตามตัวแปรช่วยให้เราเลือกทดสอบเฉพาะเส้นทางที่ส่งผลต่อข้อมูลโดยตรง ทำให้เจอบั๊กได้ตรงจุด และไม่ต้องเสียเวลาทดสอบทุกเส้นทางที่เป็นไปได้ของ Control Flow ทั้งหมด |

## หน้า 6: STEP 3 เรียนรู้ Def-Use Pair และ Def-Clear Path

กำหนดหมายเลขโหนดเพื่อการวิเคราะห์:
* **โหนด 1 (บรรทัด 547):** `Def(age)` [คำนวณ `now.getFullYear() - d.getFullYear()`]
* **โหนด 2 (บรรทัด 548 if):** ตรวจสอบเดือน/วันเกิด
* **โหนด 3 (บรรทัด 548 body):** `C-use(age)`, `Def(age)` [`age--`]
* **โหนด 4 (บรรทัด 549 if):** `P-use(age)` [`age < 18`]
* **โหนด 5 (บรรทัด 549 body):** Return error "อายุไม่ครบ 18 ปีบริบูรณ์"
* **โหนด 6 (บรรทัด 550 if):** `P-use(age)` [`age > 80`]
* **โหนด 7 (บรรทัด 550 body):** Return error "กรุณาตรวจสอบปีเกิดอีกครั้ง"
* **โหนด 8 (บรรทัด 551):** Return null (ผ่าน)

**ตารางจับคู่ Def-Use:**

| Def จุดที่ | Use จุดที่ | เป็น Def-Use Pair หรือไม่? | เหตุผล |
| :---: | :---: | :---: | :--- |
| **โหนด 1 (บรรทัด 547)** | **โหนด 3 (บรรทัด 548)** | **[x] ใช่** [ ] ไม่ใช่ | เป็นเส้นทางตรงจากจุดกำหนดค่าแรกไปยังคำสั่ง `age--` โดยไม่มีคำสั่งกำหนดค่า `age` อื่นมาคั่นกลาง (Def-clear path) |

## หน้า 7: MISSION 2 — TRACE THE DATA (ต่อ)

### STEP 4: ค้นหา “3 ขั้นตอน” ของ Data Flow Testing

| ขั้นตอน | สิ่งที่ฉันเข้าใจ |
| :---: | :--- |
| **1** | **การสร้างกราฟกระแสข้อมูล (Data Flow Graph: DFG):** นำโค้ดมาเขียนโครงสร้างกราฟตามลำดับคำสั่งและการตัดสินใจ พร้อมระบุว่าแต่ละโหนดมีตัวแปรใดเกิด `Def`, `C-use`, หรือ `P-use` |
| **2** | **การสร้างเส้นทางทดสอบ (Def-Use Paths):** คัดเลือกเส้นทางทดสอบที่เชื่อมระหว่างจุดที่นิยามค่า (Def) ไปยังจุดที่เรียกใช้ค่า (Use) โดยเป็นเส้นทางที่ค่าตัวแปรไม่ถูกเปลี่ยนแปลงระหว่างทาง (Def-Clear Path) |
| **3** | **การสร้างกรณีทดสอบ (Test Cases):** นำเส้นทาง (Paths) ที่ได้มากำหนดค่าข้อมูลนำเข้า (Test Data) ที่บังคับให้โปรแกรมวิ่งผ่านเส้นทางนั้นจริง พร้อมระบุผลลัพธ์ที่คาดหวัง (Expected Result) |

### STEP 5: สร้าง Mini Data Flow Graph (DFG)
```text
           [ (1) Def(age) ]
                  │
                  ▼
          [ (2) ตรวจสอบวันเกิด ]
            /            \
  (ยังไม่ถึงวันเกิด)      (ถึงวันเกิดแล้ว)
          /                \
         ▼                  │
[ (3) C-use(age), Def(age) ]│
         \                  │
          \                /
           ▼              ▼
           [ (4) P-use(age): age < 18 ]
              /              \
         (จริง)              (เท็จ)
            /                  \
           ▼                    ▼
   [ (5) Return Error ]   [ (6) P-use(age): age > 80 ]
                               /             \
                          (จริง)             (เท็จ)
                             /                 \
                            ▼                   ▼
                   [ (7) Return Error ]  [ (8) Return null ]
```

### STEP 6: สร้าง Def-Use Paths (หน้า 7–8)

| Path | เส้นทางที่ฉันพบ | Def -> Use ที่เกี่ยวข้อง |
| :---: | :--- | :--- |
| **Path-1** | `1 -> 2 -> 3 -> 4 -> 5` | `Def(โหนด 3) -> P-use(โหนด 4)` (ยังไม่ถึงวันเกิด ลดอายุ 1 ปีแล้วอายุ < 18) |
| **Path-2** | `1 -> 2 -> 3 -> 4 -> 6 -> 8` | `Def(โหนด 3) -> P-use(โหนด 4), P-use(โหนด 6)` (ลดอายุ 1 ปีแล้วอายุอยู่ในเกณฑ์ 18–80) |
| **Path-3** | `1 -> 2 -> 4 -> 6 -> 8` | `Def(โหนด 1) -> P-use(โหนด 4), P-use(โหนด 6)` (ถึงวันเกิดแล้ว ไม่ลดอายุ และอายุอยู่ในเกณฑ์) |
| **Path-4** | `1 -> 2 -> 4 -> 6 -> 7` | `Def(โหนด 1) -> P-use(โหนด 4), P-use(โหนด 6)` (ถึงวันเกิดแล้ว และอายุเกิน 80 ปี) |

## หน้า 9–10: STEP 3 ถ้าพบ FAIL ให้ตรวจสอบว่าเป็น Bug หรือไม่

*(ในการทดสอบระบบของเว็บไซต์ เราได้ทำการทดสอบช่อง **"ข้อมูลเพิ่มเติม" (`#note`)** ด้วยเทคนิค Boundary Value Analysis ที่จุด 300 ตัวอักษร)*

* **Expected กับ Actual ต่างกันตรงไหน?**
  > สเปกระบุว่าข้อความเพิ่มเติมต้อง *"ไม่เกิน 300 ตัวอักษร"* ดังนั้นเมื่อกรอก 300 ตัวอักษรพอดี ผลที่คาดหวัง (Expected Result) คือต้อง **"ผ่าน"** แต่ผลที่เกิดขึ้นจริง (Actual Result) ระบบกลับขึ้นเตือนสีแดงว่า **"ข้อความยาวเกิน 300 ตัวอักษร" (ไม่ผ่าน)**

* **มีหลักฐานอะไรยืนยัน?**
  > โค้ดในบรรทัดที่ 586 ระบุคำสั่ง:  
  > `return $("#note").value.length >= 300 ? "ข้อความยาวเกิน 300 ตัวอักษร" : null;`  
  > ซึ่งเขียนเงื่อนไขเป็น `>= 300` แทนที่จะเป็น `> 300` และบนหน้าจอมีตัวนับแสดง `300 / 300` (ตัวนับยังเป็นสีปกติ) แต่กลับถูกระบบปฏิเสธ

* **คิดว่าเป็น Defect/Bug หรือไม่? เพราะอะไร?**
  > **เป็น Bug (Defect)** อย่างแน่นอน เพราะพฤติกรรมการทำงานของระบบขัดแย้งกับข้อกำหนดความต้องการ (Specification) และขัดแย้งกับ UI Counter ทำให้ผู้สมัครที่พิมพ์ข้อความพอดี 300 ตัวอักษรไม่สามารถส่งใบสมัครได้

## หน้า 15: REFLECTION — ฉันเข้าใจ Data Flow Testing แล้วหรือยัง?

**1. ก่อนทำกิจกรรมนี้ ฉันคิดว่า Test Case เกิดขึ้นจากอะไร?**
> *"ก่อนทำกิจกรรมนี้ ฉันคิดว่า Test Case เกิดจากการคาดเดาความรู้สึกของผู้ใช้งาน การสุ่มใส่ข้อมูลแปลก ๆ เข้าไป หรือดูเฉพาะหน้าจอ UI ภายนอกเท่านั้น โดยไม่ได้พิจารณาโครงสร้างโค้ดภายใน"*

**2. หลังทำกิจกรรมนี้ ฉันเห็นความสัมพันธ์ระหว่าง Source Code กับ Test Case อย่างไร?**
> *"หลังทำกิจกรรมนี้ ฉันเห็นว่า Test Case มีความสัมพันธ์แนบแน่นกับ Source Code โดยทุก Test Case ถูกสร้างขึ้นมาเพื่อบังคับให้ตัวแปรในโค้ดเดินทางผ่านเส้นทาง Def-Use ที่เฉพาะเจาะจง ทำให้การทดสอบมีเหตุผลรองรับทางคณิตศาสตร์และโครงสร้างโค้ด"*

**3. Def และ Use ช่วยให้ฉันมองหาเส้นทางทดสอบได้อย่างไร?**
> *"ช่วยเป็นเข็มทิศชี้ทาง โดยให้ความสำคัญเฉพาะจุดที่ตัวแปรถูกสร้าง/เปลี่ยนแปลง (Def) และจุดที่ถูกนำไปใช้จริง (Use) ทำให้เราตัดกิ่งก้านที่ไม่จำเป็นใน Control Flow ออกไปได้ และเลือกทดสอบเฉพาะเส้นทางที่ส่งผลกระทบต่อข้อมูลอย่างแท้จริง"*

**4. จุดไหนของกิจกรรมที่ฉันยังไม่เข้าใจ และต้องการให้อาจารย์อธิบายเพิ่ม?**
> *"อยากให้อาจารย์อธิบายเพิ่มเติมเกี่ยวกับการวิเคราะห์ Data Flow ข้ามฟังก์ชันหรือข้ามออบเจกต์ (Inter-procedural Data Flow) ในระบบที่มีสถาปัตยกรรมขนาดใหญ่ และการเลือกเกณฑ์ความครอบคลุม (Coverage Criteria) เช่น All-Defs vs All-Uses"*

**5. ถ้าต้องกลับไปทดสอบเว็บไซต์ของตนเองอีกครั้ง ฉันจะปรับวิธีคิด/วิธีทดสอบอย่างไร?**
> *"จะไม่ทดสอบแบบสุ่มเดาอีกต่อไป แต่จะเปิด Source Code ดูตัวแปรที่รับผิดชอบ Business Logic สำคัญ วิเคราะห์ Data Map และ Def-Use Pair เพื่อแปลงเส้นทางเป็นตาราง Test Case ที่ครอบคลุมค่าขอบเขตและเงื่อนไขทั้งหมดก่อนเริ่มทดสอบระบบ"*
