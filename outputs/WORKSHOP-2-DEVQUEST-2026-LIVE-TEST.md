## หน้า 3: MISSION 1 — FIND THE DATA

### STEP 1: เลือกตัวแปรจริง
* **ชื่อตัวแปร:** `age` (ตัวแปรคำนวณอายุในกฎการตรวจสอบวันเกิด `birthDate` ของระบบ)
* **ชนิดข้อมูล:** `number` (Integer)
* **เหตุผลที่เลือกตัวแปรนี้:**
  > ตัวแปร `age` ในฟังก์ชันตรวจสอบวันเกิด (`birthDate.validate` บรรทัดที่ 23–37 ใน `outputs/script.js` บนเว็บไซต์จริง) เป็นตัวแปรที่มีบทบาทสำคัญในการควบคุม Business Rule ของ DevQuest 2026 (ผู้สมัครต้องมีอายุไม่ต่ำกว่า 15 ปีบริบูรณ์) มีการกำหนดค่าเริ่มต้นจากการคำนวณปี (Def), มีการนำค่าไปลดทอนตามเงื่อนไขเดือน/วันเกิด (C-use และ Re-def), และถูกนำไปใช้ในนิพจน์เงื่อนไขตัดสินใจ (P-use) เพื่อควบคุมผลการตรวจสอบความถูกต้องก่อนคืนค่า จึงแสดงพฤติกรรมการไหลของข้อมูล (Data Flow) ได้อย่างชัดเจน ครบถ้วนตามทฤษฎี

### STEP 2: หา Def และ Use

**Source Code จริงบนเว็บไซต์ (`outputs/script.js` บรรทัดที่ 23–37):**
```javascript
23: birthDate: {
24:   message: 'Applicants must be at least 15 years old.',
25:   validate: value => {
26:     if (!value) return false;
27:     const d = new Date(value);
28:     const now = new Date();
29:     if (isNaN(d.getTime()) || d > now) return false;
30:     let age = now.getFullYear() - d.getFullYear();
31:     const m = now.getMonth() - d.getMonth();
32:     if (m < 0 || (m === 0 && now.getDate() < d.getDate())) {
33:       age--;
34:     }
35:     return age >= 15;
36:   }
37: },
```

**ตารางแจกแจง Def และ Use ของตัวแปร `age`:**

| ลำดับ/บรรทัด | เกิดอะไรขึ้นกับตัวแปร? | ฉันจัดเป็น | หลักฐาน/เหตุผล |
| :---: | :--- | :---: | :--- |
| **บรรทัด 30** | `let age = now.getFullYear() - d.getFullYear();` | **[x] Def**<br>[ ] Use | มีการประกาศตัวแปรและกำหนดค่าเริ่มต้นด้วยเครื่องหมาย `=` โดยคำนวณปีปัจจุบันลบด้วยปีเกิด |
| **บรรทัด 33 (ก)** | `age--` (ส่วนดึงค่ามาคำนวณ: `age - 1`) | [ ] Def<br>**[x] Use** | มีการเรียกอ่านค่าปัจจุบันของ `age` ไปลบออก 1 ทางคณิตศาสตร์ (**C-use**) |
| **บรรทัด 33 (ข)** | `age--` (ส่วนบันทึกค่ากลับ: `age = ...`) | **[x] Def**<br>[ ] Use | มีการอัปเดตและเขียนทับค่าใหม่ลงในตัวแปร `age` เดิม (**Re-define**) |
| **บรรทัด 35** | `return age >= 15;` (ส่วนเปรียบเทียบเงื่อนไข `>= 15`) | [ ] Def<br>**[x] Use** | นำค่าตัวแปร `age` ไปใช้ในนิพจน์เงื่อนไขเปรียบเทียบทางตรรกะว่ามากกว่าหรือเท่ากับ 15 หรือไม่ (**P-use**) |
| **บรรทัด 35** | `return age >= 15;` (ส่วนส่งค่าผลลัพธ์ boolean ออกไป) | [ ] Def<br>**[x] Use** | ส่งผลลัพธ์จากการคำนวณคืนไปยังฟังก์ชัน `validateField` เพื่อนำไปอัปเดต UI หน้าเว็บ (**C-use**) |

| ตำแหน่ง (บรรทัด) | ตัวแปร | P-use หรือ C-use? | เหตุผลสั้น ๆ |
| :---: | :---: | :---: | :--- |
| **บรรทัด 33** | `age` | **C-use** | ถูกนำไปใช้คำนวณทางคณิตศาสตร์ (ลบค่าลง 1 ในคำสั่ง `age--`) |
| **บรรทัด 35** | `age` | **P-use** | ถูกนำไปใช้ในนิพจน์เงื่อนไขการตัดสินใจ (`age >= 15`) เพื่อประเมินค่าจริง/เท็จ |
| **บรรทัด 35** | `age >= 15` | **C-use** | ส่งผลลัพธ์บูลีนที่ได้จากการคำนวณคืนกลับไปให้ฟังก์ชันภายนอกประมวลผลต่อ |

### หยุดคิดก่อนเรียนคำศัพท์ต่อ
* **คำถาม:** ถ้าไม่มีคำว่า Def / Use / P-use / C-use เราจะอธิบายการเดินทางของค่าตัวแปรนี้ด้วยภาษาของเราเองว่าอย่างไร?
* **คำตอบ:**
  > "ตัวแปร `age` ถือกำเนิดขึ้นมาจากการ **'ตั้งต้นคำนวณ'** ด้วยการเอาปีปัจจุบันลบด้วยปีเกิดของผู้สมัคร จากนั้นเดินทางต่อไปยังจุดตรวจว่าถึงวันเกิดปีนี้หรือยัง ถ้ายังไม่ถึงจะถูก **'ปรับลดยอดลง 1 ปี'** แล้วค่าอายุจริงจะถูกส่งต่อไป **'ตรวจวัดเกณฑ์ขั้นต่ำ'** ว่าอายุถึง 15 ปีบริบูรณ์หรือไม่ ($\ge 15$) ก่อนที่จะส่ง **'คำตอบผ่าน/ไม่ผ่าน'** ไปแสดงผลบนหน้าจอเว็บไซต์ DevQuest 2026"

## หน้า 5: MISSION 2 — TRACE THE DATA

### STEP 1: วาด Data Map อย่างง่าย
```text
[Def] คำนวณปีปัจจุบัน - ปีเกิด -> let age (บรรทัด 30)
       │
       ▼
   ตรวจเดือนและวันเกิด (บรรทัด 32)
   ├── (ยังไม่ถึงวันเกิดในปีนี้: m < 0 หรือ วันที่ยังไม่ถึง) ──► [C-use & Re-Def] ปรับลดค่า age-- (บรรทัด 33)
   │                                                                      │
   └── (ถึงวันเกิดแล้วในปีนี้) ─────────────────────────────────────────────┘
       │
       ▼
[P-use] ตรวจสอบเงื่อนไขเกณฑ์อายุ age >= 15 (บรรทัด 35)
   ├── (จริง: true)  ──► คืนค่า true  -> validateField เคลียร์กรอบแดง / ผ่านเกณฑ์
   └── (เท็จ: false) ──► คืนค่า false -> validateField ขึ้นกรอบแดงเตือน "Applicants must be at least 15 years old."
```
*(เขียนสรุปย่อตามแนวคิดใบงาน:)*  
`Def (คำนวณอายุจากปี) -> P-use (ตรวจวันเกิด) -> C-use & Def (ลดอายุ 1 ปี) -> P-use (เช็ก >= 15) -> คืนผลลัพธ์`

### STEP 2: เรียนรู้ Data Flow Testing

| คำถาม | คำตอบของฉัน |
| :--- | :--- |
| **Data Flow Testing มองอะไรในโปรแกรม?** | DFT มอง **"พฤติกรรมและวงจรชีวิตของข้อมูล (Data Lifecycle)"** ตลอดการประมวลผลของโปรแกรม โดยมุ่งเน้นติดตามว่าตัวแปรถูกสร้าง/กำหนดค่าที่ไหน (Define), ถูกนำไปคำนวณที่ไหน (C-use), และถูกนำไปใช้เป็นเงื่อนไขตัดสินใจที่ไหน (P-use) เพื่อตรวจสอบความถูกต้องของการเคลื่อนย้ายข้อมูล |
| **ทำไมการติดตามตัวแปรจึงช่วยในการทดสอบ?** | เพราะข้อบกพร่องส่วนใหญ่ในโปรแกรมมักเกิดจากการที่ข้อมูลมีสถานะไม่ถูกต้อง (เช่น ข้อมูลไม่ผ่านการคำนวณ, ค่าถูกเขียนทับก่อนใช้, หรือค่าขอบเขตผิดพลาด) การติดตามตัวแปรช่วยให้เราออกแบบกรณีทดสอบที่เจาะจงเส้นทางการไหลของข้อมูลที่สำคัญได้โดยตรง ช่วยลดจำนวนการทดสอบที่ซ้ำซ้อนและครอบคลุมจุดเสี่ยงได้ดีกว่าการสุ่มทดสอบเส้นทางใน Control Flow |

## หน้า 6: STEP 3 เรียนรู้ Def-Use Pair และ Def-Clear Path

กำหนดหมายเลขโหนดของฟังก์ชันตรวจสอบวันเกิด:
* **โหนด 1 (บรรทัด 26–29):** รับค่า `value` และตรวจความถูกต้องเบื้องต้น (`!value`, รูปแบบวันที่, ไม่ใช่วันในอนาคต)
* **โหนด 2 (บรรทัด 30):** `Def(age)` [คำนวณ `now.getFullYear() - d.getFullYear()`]
* **โหนด 3 (บรรทัด 31–32 if):** ตรวจสอบว่าถึงวันเกิดปีนี้หรือยัง (`m < 0 || ...`)
* **โหนด 4 (บรรทัด 33 body):** `C-use(age)`, `Def(age)` [`age--`]
* **โหนด 5 (บรรทัด 35):** `P-use(age)` ตรวจสอบเงื่อนไข `age >= 15`
* **โหนด 6 (บรรทัด 35 true):** คืนค่า `true` (อายุผ่านเกณฑ์ $\ge 15$)
* **โหนด 7 (บรรทัด 35 false):** คืนค่า `false` (อายุไม่ผ่านเกณฑ์ $< 15$)

**ตารางจับคู่ Def-Use:**

| Def จุดที่ | Use จุดที่ | เป็น Def-Use Pair หรือไม่? | เหตุผล |
| :---: | :---: | :---: | :--- |
| **โหนด 2 (บรรทัด 30)** | **โหนด 4 (บรรทัด 33)** | **[x] ใช่** [ ] ไม่ใช่ | เป็นเส้นทางตรงจากจุดกำหนดค่าแรกไปยังคำสั่ง `age--` โดยไม่มีคำสั่งกำหนดค่า `age` อื่นมาคั่นกลาง (Def-clear path) |
| **โหนด 2 (บรรทัด 30)** | **โหนด 5 (บรรทัด 35)** | **[x] ใช่** [ ] ไม่ใช่ | ในเส้นทาง `2 -> 3 -> 5` (กรณีถึงวันเกิดแล้ว ข้ามโหนด 4) ค่าจากโหนด 2 เดินทางมาถึงเงื่อนไข `age >= 15` โดยไม่มีการ Def ค่าใหม่คั่น |
| **โหนด 4 (บรรทัด 33)** | **โหนด 5 (บรรทัด 35)** | **[x] ใช่** [ ] ไม่ใช่ | ค่าที่ถูกลดค่าลง 1 ในโหนด 4 เดินทางต่อไปยังเงื่อนไข `age >= 15` ในโหนด 5 ทันที โดยไม่มีการกำหนดค่าซ้ำ |
| **โหนด 2 (บรรทัด 30)** | **โหนด 5 (บรรทัด 35)** *(ผ่านโหนด 4)* | [ ] ใช่ **[x] ไม่ใช่** | หากเดินผ่านเส้นทาง `2 -> 3 -> 4 -> 5` ค่าจากโหนด 2 จะถูกเขียนทับ (Re-define) ที่โหนด 4 ก่อนถึงโหนด 5 จึงไม่ใช่ Def-clear path ของโหนด 2 |

## หน้า 7: MISSION 2 — TRACE THE DATA (ต่อ)

### STEP 4: ค้นหา “3 ขั้นตอน” ของ Data Flow Testing

| ขั้นตอน | สิ่งที่ฉันเข้าใจ |
| :---: | :--- |
| **1** | **การสร้างกราฟกระแสข้อมูล (Data Flow Graph: DFG):** นำโค้ดฟังก์ชันมากำหนดหมายเลขโหนดและวาดทิศทางการประมวลผล พร้อมทั้งเขียนกำกับว่าแต่ละโหนดเกิด `Def`, `C-use`, หรือ `P-use` สำหรับตัวแปรใด |
| **2** | **การสร้างเส้นทางทดสอบ (Def-Use Paths):** คัดเลือกเส้นทางทดสอบที่เชื่อมระหว่างจุดที่ตัวแปรถูกกำหนดค่า (Def) ไปยังจุดที่ถูกเรียกใช้ (Use) โดยเป็นเส้นทางที่ค่าตัวแปรไม่ถูกเปลี่ยนแปลงระหว่างทาง (Def-Clear Path) |
| **3** | **การสร้างกรณีทดสอบ (Test Cases):** ออกแบบชุดข้อมูลนำเข้า (Test Data) ที่บังคับให้โปรแกรมประมวลผลวิ่งผ่านแต่ละ Path ที่เลือกไว้จริง พร้อมระบุผลลัพธ์ที่คาดหวัง (Expected Result) |

### STEP 5: สร้าง Mini Data Flow Graph (DFG)
```text
                  [ โหนด 1: ตรวจวันที่เบื้องต้น ]
                                │
                                ▼
                  [ โหนด 2: Def(age) ]  (บรรทัด 30)
                                │
                                ▼
                  [ โหนด 3: ตรวจสอบเดือน/วันเกิด ] (บรรทัด 32)
                       /                 \
            (ยังไม่ถึงวันเกิด)        (ถึงวันเกิดแล้ว)
                     /                     \
                    ▼                       │
    [ โหนด 4: C-use(age), Def(age) ]        │
                    \                       │
                     \                     /
                      ▼                   ▼
                  [ โหนด 5: P-use(age) age >= 15 ] (บรรทัด 35)
                            /         \
                      (จริง)           (เท็จ)
                        /                 \
                       ▼                   ▼
           [ โหนด 6: Return true ]  [ โหนด 7: Return false ]
```

### STEP 6: สร้าง Def-Use Paths (หน้า 7–8)

| Path | เส้นทางที่ฉันพบ | Def -> Use ที่เกี่ยวข้อง |
| :---: | :--- | :--- |
| **Path-1** | `1 -> 2 -> 3 -> 4 -> 5 -> 7` | `Def(โหนด 4) -> P-use(โหนด 5)` (ยังไม่ถึงวันเกิด ปรับลดอายุลง 1 ปีแล้วอายุ $< 15$ ปี $\rightarrow$ ไม่ผ่าน) |

## หน้า 15: REFLECTION — ฉันเข้าใจ Data Flow Testing แล้วหรือยัง?

**1. ก่อนทำกิจกรรมนี้ ฉันคิดว่า Test Case เกิดขึ้นจากอะไร?**
> *"ก่อนทำกิจกรรมนี้ ฉันคิดว่า Test Case เกิดจากการสุ่มข้อมูลทดสอบตามความรู้สึก หรือดูจากหน้าตา UI แล้วลองพิมพ์ค่าต่าง ๆ ลงไปดูว่าจะเกิด Error หรือไม่ โดยไม่ได้รู้ว่าโค้ดหลังบ้านประมวลผลอย่างไร"*

**2. หลังทำกิจกรรมนี้ ฉันเห็นความสัมพันธ์ระหว่าง Source Code กับ Test Case อย่างไร?**
> *"หลังทำกิจกรรมนี้ ฉันเห็นว่า Source Code กับ Test Case มีความสัมพันธ์กันโดยตรงแบบ 1 ต่อ 1 โดย Test Case ถูกสร้างขึ้นมาเพื่อบังคับให้ตัวแปรใน Source Code ไหลไปตามเส้นทาง Def-Use ที่เราต้องการพิสูจน์ ทำให้การทดสอบมีหลักการและเหตุผลรองรับทางโครงสร้างโปรแกรม"*

**3. Def และ Use ช่วยให้ฉันมองหาเส้นทางทดสอบได้อย่างไร?**
> *"ช่วยให้เราจับจุดวิกฤตของข้อมูลได้ชัดเจน โดยโฟกัสเฉพาะจุดที่ตัวแปรถูกสร้าง/เปลี่ยนแปลงค่า (Def) และจุดที่ถูกนำไปใช้คำนวณหรือตัดสินใจ (Use) ทำให้เราตัดเส้นทางที่ไม่จำเป็นออกไป และทดสอบเฉพาะเส้นทางที่ส่งผลต่อผลลัพธ์ของระบบจริง ๆ"*

**4. จุดไหนของกิจกรรมที่ฉันยังไม่เข้าใจ และต้องการให้อาจารย์อธิบายเพิ่ม?**
> *"อยากให้อาจารย์อธิบายเพิ่มเติมเกี่ยวกับการทำ Data Flow Testing ร่วมกับการทำงานแบบ Asynchronous (เช่น Event Listener, Promise, Fetch API) ว่ามีหลักการสร้าง DFG และการหา Def-Clear Path อย่างไรเมื่อจังหวะเวลาในการทำงานไม่เป็นเส้นตรง"*

**5. ถ้าต้องกลับไปทดสอบเว็บไซต์ของตนเองอีกครั้ง ฉันจะปรับวิธีคิด/วิธีทดสอบอย่างไร?**
> *"ฉันจะเปิด Source Code ดูตัวแปรหลักที่มีการคำนวณและเงื่อนไขซับซ้อนก่อน แล้ววาดแผนภาพ Data Map หรือ DFG เพื่อหา Def-Use Pair จากนั้นจึงแปลงแต่ละ Path ออกมาเป็นชุด Test Case ที่ครอบคลุมทั้งค่าปกติ ค่าขอบเขต และค่าผิดพลาด ก่อนลงมือทดสอบจริงบนหน้าเว็บ"*
